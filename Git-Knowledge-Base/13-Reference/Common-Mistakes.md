# Common Mistakes: 8 ข้อผิดพลาดสุดคลาสสิกใน Git และวิธีป้องกัน

รวบรวมความเข้าใจผิดและหลุมพรางทางเทคนิคที่นักพัฒนามักประสบ พร้อมคำอธิบายสาเหตุและวิธีหลีกเลี่ยง

---

## 1. เข้าใจผิดว่า `git add` คือการ Commit ไฟล์เข้า Repository
- **ความเข้าใจผิด:** คิดว่าสั่ง `git add` ปุ๊บ โค้ดจะถูกบันทึกเป็นประวัติศาสตร์ถาวรแล้ว
- **ความจริง:** `git add` เป็นเพียงการนำภาพถ่ายของไฟล์เข้าสู่ **Staging Area (Index)** เท่านั้น หากไม่สั่ง `git commit` การเปลี่ยนแปลงนั้นจะยังไม่เป็นประวัติถาวร
- **แนวทางป้องกัน:** ตรวจสอบ `git status` เสมอ และอย่าลืมรัน `git commit -m "..."` เมื่อพร้อม

---

## 2. เข้าใจผิดว่า `git fetch` คือการ Pull โค้ดลงเครื่อง
- **ความเข้าใจผิด:** พิมพ์ `git fetch` แล้วสงสัยว่าทำไมโค้ดที่เพื่อนแก้ถึงยังไม่ปรากฏในไฟล์บน IDE ของตนเอง
- **ความจริง:** `fetch` ดาวน์โหลดเฉพาะออบเจกต์และอัปเดต Remote-tracking branches (`origin/main`) โดย **ไม่แตะต้อง Working Tree ของคุณเลย** หากต้องการให้โค้ดมารวมในไฟล์จริง ต้องสั่ง `git merge` หรือใช้ `git pull`

---

## 3. มโนภาพว่า Branch คือโฟลเดอร์ทางกายภาพ
- **ความเข้าใจผิด:** คิดว่าเมื่อสั่งแตก Branch Git จะไป Copy โฟลเดอร์ใหม่บนดิสก์
- **ความจริง:** ใน Git แบบปกติ Branch มีโฟลเดอร์ทางกายภาพเพียงโฟลเดอร์เดียว Branch เป็นเพียง **Pointer ขนาด 41 ไบต์** ชี้ไปยัง Commit หากต้องการโฟลเดอร์ทางกายภาพแยกจริงเพื่อทำงานพร้อมกัน ต้องใช้ [[Worktree-Concept]]

---

## 4. เข้าใจผิดว่า HEAD คือชื่อของ Branch
- **ความเข้าใจผิด:** สับสนระหว่าง Branch กับ HEAD
- **ความจริง:** Branch คือสายการทำงาน ส่วน **HEAD คือตัวชี้ตำแหน่งปัจจุบัน** ว่าตัวเรากำลังยืนอยู่ ณ จุดใด (มักจะชี้ไปที่ชื่อ Branch อีกทีหนึ่ง)

---

## 5. เผลอใช้ `git reset --hard` โดยไม่ตรวจสอบ
- **ความเข้าใจผิด:** คิดว่า reset hard จะสามารถกู้คืนโค้ดที่พิมพ์ค้างไว้ในเครื่องได้
- **ความจริง:** การเปลี่ยนแปลงใน Working Tree ที่ **ยังไม่ได้ Commit** หากโดน `git reset --hard` กวาดทิ้ง จะสูญหายอย่างถาวร 100% กู้ผ่าน Reflog ไม่ได้!
- **แนวทางป้องกัน:** ก่อนใช้ `--hard` ให้รัน `git status` หรือ `git stash` เก็บงานค้างไว้ก่อนเสมอ

---

## 6. Rebase ประวัติศาสตร์ที่เป็น Public / Shared Branch
- **ความเข้าใจผิด:** รัน `git rebase` บนกิ่ง `main` หรือกิ่งที่เพื่อนร่วมทีมกำลังทำงานร่วมกันอยู่
- **ความจริง:** Rebase เปลี่ยนค่า Commit Hash ทั้งหมด ทำให้ประวัติของเพื่อนกับของคุณแตกออกจากกัน ก่อให้เกิดหายนะ Merge Conflict มหาศาลเมื่อ Push
- **กฎเหล็ก:** Rebase เฉพาะ Local/Private Branch ของตนเองเท่านั้น

---

## 7. ใช้ Force Push (`git push -f`) พร่ำเพรื่อ
- **ความเข้าใจผิด:** พอเซิร์ฟเวอร์ปฏิเสธ Push ก็ใส่ธง `-f` เพื่อบังคับทับ
- **ความจริง:** การ Force push จะไปลบและเขียนทับ Commit ของเพื่อนร่วมทีมที่เพิ่งส่งขึ้นเซิร์ฟเวอร์ทิ้งไปทันที
- **แนวทางป้องกัน:** หากจำเป็นต้อง Force push จริงๆ (เช่น หลังจัดระเบียบ Commit ในกิ่งตัวเอง) ให้ใช้ `--force-with-lease` แทนเสมอ ซึ่งระบบจะยกเลิกคำสั่งหากมีคนอื่น push แทรกขึ้นมาก่อน

---

## 8. แก้ไข Merge Conflict เสร็จแล้วลืมรันชุดทดสอบ (Test)
- **ความเข้าใจผิด:** ลบ Conflict Markers เสร็จแล้วรีบกด Commit ทันทีโดยไม่ได้รันโค้ด
- **ความจริง:** การรวมโค้ดอาจทำให้เกิดปัญหาตรรกะชนกันในระดับ Business Logic ได้ แม้ syntax จะไม่ error
- **แนวทางป้องกัน:** ต้องสั่ง `npm test` หรือรันบิลด์ทดสอบก่อนสั่ง `git merge --continue` ทุกครั้ง
